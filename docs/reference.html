§ 1 · Speculative technology

Read this before trusting any fusion or antimatter number

Every chip on this site links here.

Micro-fusion and antimatter reactors do not exist at the parameters modeled here. PowerPlan includes them as what-if instruments: the simulator treats them as just another generator subclass, so you can ask “what would a grid look like if a box like this existed” — not “what will a fusion plant cost.” Specifically:

  • Costs are intentionally optimistic inputs. Fusion capital cost spans $9k–27k/kW (a $15k/kW first-of-a-kind base with size discounts down to ×0.6 and a ×1.8 premium for the harder p-B11 cycle); antimatter spans $50k–100k/kW (a $100k/kW base, ×0.5 above 20 MW). Q-values, conversion efficiencies, maintenance intervals and the antiproton fuel price (implicitly zero) are all parameters to vary, not forecasts.
  • The antimatter “target atom” pathway is author-invented. Directing antiprotons at xenon, lead, or uranium targets to harvest Auger and ionization electrons on graphene electrodes — including the antimatter-catalyzed-fission amplification factor (×1.107 for U-238) and the electron_collection_efficiency of 0.45 — has no experimental basis. It is a designed mechanism, written to be internally consistent, nothing more.
  • q_engineering is reported but unused. The fusion model accepts and echoes an engineering Q in its summaries, but the power balance is derived only from thermal_efficiency minus a sustainment fraction. Changing Q changes a label, not a result.
  • Renewable accounting: fusion and antimatter count as non-renewable in every renewable-fraction metric, alongside gas.

Results that lean on these components say more about the assumptions than about the world. The five conventional sources and seven storage technologies use published-engineering parameter ranges and deserve correspondingly more trust.

§ 2 · The engine

How dispatch works

One fixed five-priority pass per timestep — straight-line code in powerplan/grid.py, not a pluggable market model.

Dispatch priority runs once per simulation tick
  1. Generation & conversion. Every source’s output_kw(hour, weather) is summed — the dispatcher never throttles a source. The weighted controller efficiency η is applied to the whole stream; what serves demand immediately is direct supply, the rest is excess.
  2. Charge storage with the excess. Units are re-sorted every step by charge_efficiency × (1 − SoC) — the most efficient, emptiest unit absorbs first, each up to its max_charge_kw.
  3. Discharge to cover remaining demand. Storage is sorted by discharge_efficiency × SoC — the most efficient, fullest unit delivers first, each up to its max_discharge_kw.
  4. Grid exchange. Still-unmet demand imports; still-uncharged excess exports. Both directions are capped by grid_interconnect_kw — set it to 0 for island mode, where neither happens.
  5. Curtailment & unmet demand. Leftover excess is curtailed (discarded); any demand still standing is recorded as unmet and feeds the resilience metrics (LOLP / LOLE / ENS, §4).
FIG. 1The fixed dispatch path. Generation flows through the controller stage onto the bus (①); excess charges storage (②); shortfall discharges it (③); the grid absorbs or supplies the remainder up to the interconnect cap (④); the rest is curtailed, or recorded as unmet demand (⑤). Arrow hues match the power-balance charts everywhere else on the site.
Engine truths easy to mis-assume — stated for the record
Controllers shape efficiency, never power.
Power is allocated across controllers in declared order up to each unit’s rating to compute a weighted η, which is then applied to all generation — power beyond the aggregate controller rating still flows, it is never clipped. With no controllers configured, a flat 0.95 is assumed.
Sources are non-dispatchable.
The dispatcher takes whatever each source model produces. The one seemingly dispatchable unit, the gas peaker, actually self-schedules inside its own model: a Gaussian ramp across 14:00–21:00 peaking near 17:30, a 15% shoulder from 10:00, ~3% standby otherwise.
Temperature drives HVAC demand only.
The ambient temperature series feeds LoadProfile.demand_kw (heating/cooling load). Sources are not thermally derated, and each storage unit’s thermal state evolves from its own power flow, not from weather.
Simulations are seed-deterministic.
Demand noise is seeded at 42 and synthetic weather at 123, so the same configuration replays bit-identically. Components mutate state in place (SoC, health, fuel reservoirs) — a rerun needs fresh instances, which the engine creates for every run.

LCOE caveat. LCOE assumes 20-year amortization at 5% discount of source + storage capex against annual generation — live runs shorter than a year feed the formula less than a year’s energy and overstate it by roughly 8760 ⁄ hours (a 720 h run reads ~12× too high; live pages print this factor next to the figure). All pre-baked numbers on this site come from full-year, 8,760 h runs.

Everything runs locally. All live simulations — Builder, Resilience, Municipal — run in your browser via Pyodide (CPython on WebAssembly) inside a web worker. The engine package downloads once; nothing you configure or run is ever uploaded.

Regenerating the baked data. The pre-computed figures (presets, comparison, projections, the resilience sample) are written by scripts/prebake.py at the repo root. Re-run it after engine changes to refresh docs/data/ and the cache-busting hashes in the data manifest.
